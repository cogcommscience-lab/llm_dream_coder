Overview

llm_dream_coder is a modular, open-source toolkit for semi-automated content analysis of dream reports using the Hall/Van de Castle (H/VdC) coding system. It uses Claude (Anthropic) as the coding engine, with detailed codebook prompts and few-shot examples derived directly from the H/VdC rulebook.

Each H/VdC coding category is implemented as an independent Python script. The tool is designed for researcher-in-the-loop use: the LLM produces candidate codes and reasoning for each dream, which researchers then review and correct. It is not intended as a fully automated black-box pipeline.

The tool is generalizable: it works on any dream report dataset without per-series configuration, hardcoded dictionaries, or fine-tuning. All coding logic derives from the published H/VdC rulebook.

Background

The Hall/Van de Castle System

Developed by Calvin Hall and Robert Van de Castle in the 1960s, the H/VdC system is the most widely used framework for quantitative dream content analysis. It provides standardized codes for:

  • Characters — who appears in the dream (number, gender, identity, age)
  • Social Interactions — how characters relate to each other (aggression, friendliness, sexuality)
  • Activities — what characters do
  • Striving — success and failure in goal pursuit
  • Emotions — emotional tone and affect
  • Misfortunes & Good Fortunes — negative and positive events
  • Settings — where the dream takes place

Standard normative data and coding manuals are available through the Dreambank project (UC Santa Cruz). This toolkit uses Dreambank dream reports and human codings as ground truth for development and evaluation.

Why LLM-based coding?

Manual H/VdC coding is reliable when performed by trained raters but is time-consuming and requires substantial expertise. Prior automated approaches have relied on keyword matching or supervised classifiers that require large labeled training sets and are difficult to maintain as codebook rules evolve.

Large language models offer an alternative: given a detailed natural-language codebook and examples, they can apply complex, multi-step classification rules without training data. This makes the approach practical for researchers who need to code large archives but lack the resources for full manual annotation.

Installation

git clone https://github.com/cogcommscience-lab/llm_dream_coder.git
cd llm_dream_coder

pip install anthropic pandas

Set your Anthropic API key as an environment variable:

# Add to ~/.zshrc or ~/.bashrc for persistence
export ANTHROPIC_API_KEY=your_key_here
API Key Security Never commit your API key to version control. Use environment variables or a secrets manager. The key should never appear in source code or be pasted into chat interfaces.

An Anthropic API key with access to claude-opus-4-6 is required. Keys can be created at console.anthropic.com.

Using your own data Ground-truth codings are optional. If you only have dream reports (no existing codes), the tool will still generate predicted codes and reasoning — it simply will not compute F1 or other evaluation metrics.

Characters Module

The Characters module identifies and codes all characters appearing in a dream report using the H/VdC character classification system. It is the first module implemented and serves as the foundation for Social Interaction coding (which references character codes).

Usage

# Default: 50 dreams from b-baseline collection
python characters.py

# Custom sample size
python characters.py --n 20

# Specific collection
python characters.py --collection norms-f

# Single dream by ID
python characters.py --dream-id b-baseline_0003

# Series mode (see below)
python characters.py --collection emma --series-mode

# Full dataset
python characters.py --all

Character Code Format

Each character receives a four-slot code: NUMBER + GENDER + IDENTITY + AGE

SlotValuesMeaning

Gender M F I J Male / Female / Indeterminate / Joint (mixed-gender group)
Identity K S U O P E and family codes Known / Stranger / Uncertain / Occupational / Prominent / Ethnic; family codes: H W D C B T M F X A Y I R

Series Mode

When processing a dream series (multiple dreams from the same dreamer), --series-mode maintains a character registry across dreams. The registry is populated only from relationships explicitly stated in the dream text — for example, "my husband Frank" or "my daughter Wendy." It is never inferred or assumed.

As each dream is processed, the model may return registry_updates — new name-to-code mappings extracted from that dream's text. These are merged into the registry before the next dream is processed. The registry is printed at the end of a series run for inspection. 

python characters.py --collection emma --series-mode
When to use series mode Use --series-mode when: (1) your data is a dream series from a single dreamer, and (2) you want the classifier to carry forward character identities explicitly established in earlier dreams. It has no effect on normative collections (one dream per person) and is disabled by default.

Evaluation

F1 is computed at the attribute level, not the whole-code level. Each H/VdC code is decomposed into its constituent slots — number, gender, identity, age (and ANI/CZZ type for animals/creatures) — and F1 is computed via Counter intersection over those (slot, value) tuples. This gives partial credit when the model gets 3 of 4 attributes right (e.g., predicting 1MKA when the truth is 1FKA is no longer treated as a total miss).

The module reports two attribute-level F1 scores:

  • Overall F1 (attribute-level) — computed across all character codes, including family/relative codes.
  • Non-family F1 (attribute-level) — excludes family/relative identity codes (H, W, D, C, B, T, M, F, X, A, Y, I, R). These codes require biographical knowledge of the dreamer that is not present in individual dream texts. This is the primary metric for evaluating the generalizable tool.

Emma's lower scores reflect annotator biographical knowledge bias: Dreambank coders working on the emma series had personal knowledge of the dreamer and applied family codes from dream 1, even when the dream text alone does not support them. A generalizable single-dream classifier cannot recover this information. Normative collections — where each dream comes from a different anonymous individual — are the most appropriate benchmark for a generalizable tool.

Social Interactions Module — In Progress

The Social Interactions module codes all aggressive (agg), friendly (fri), and sexual (sex) interactions in a dream report. Each interaction is a four-field tuple: (init, rec, type, code) where init and rec are character codes (or D for the dreamer), type is one of agg/fri/sex, and code combines a sub-type number with a direction symbol (> one-way, = mutual, R rejected, * self-directed).

python social_interactions.py --collection norms-f --n 50

This gives partial credit when, for example, the type and sub-type are correct but the character code is mis-coded.

Activities Module — In Progress

The Activities module codes what every character (and the dreamer) does in a dream. Each activity is a three-field tuple: (init, rec, code) where init is the actor, rec is the recipient (or null for solo acts), and code is a sub-type letter plus an optional direction modifier (> directed, = mutual, R reciprocated).

Eight sub-types: P (Physical), M (Movement on foot), L (Locomotion by vehicle), V (Verbal), S (Visual), A (Auditory), E (Expressive), C (Cognitive).

python activities.py                           # 50 norms-f dev dreams
python activities.py --n 20                    # specific number
python activities.py --collection norms-f      # full collection

Known Limitations

Family and relative codes

Family/relative identity codes (H, W, D, C, B, T, M, F, X, A, Y, I, R) require biographical knowledge of the dreamer that is not present in single dream texts. Annotators working on dream series often had this information from external sources; a text-only classifier cannot recover it. For this reason, non-family F1 is reported as the primary evaluation metric.

--series-mode partially addresses this by building a registry from explicitly stated relationships in the text (e.g., "my husband Frank"), but cannot recover codes that annotators assigned based on biographical knowledge never mentioned in any dream report.

Annotator biographical knowledge bias

Dream series coded by researchers who personally knew the dreamer will show lower F1 on identity codes regardless of classifier quality. This is a property of the ground-truth data, not the classifier. Normative collections (one dream per anonymous individual) are not affected.

API cost

claude-opus-4-6 is used for accuracy. Expect approximately $0.02–0.05 per dream at current API pricing. Prompt caching (cache_control: ephemeral) is applied to the system prompt, substantially reducing cost for large batches where the codebook is sent once and reused.

JSON parse errors

Very long dream reports occasionally produce malformed JSON output. The parser attempts two recovery strategies (code-fence extraction, then brace-matching), but failures are possible. Failed dreams are logged, skipped, and appear in the results CSV with None values for all metrics.

FAQ

Can I use this with dream data that has no ground-truth codings?

Yes. If dreambank_codings.csv does not contain entries for your dreams, the tool skips evaluation and outputs predicted codes and reasoning only. The f1, precision, and recall columns in the results CSV will be empty.

Which Anthropic model does this use and can I change it?

The default model is claude-opus-4-6, chosen for its strong instruction-following on multi-step classification tasks. You can change the MODEL constant at the top of each script to use a different model. Note that smaller or less capable models will produce lower F1 scores.

How should I interpret the reasoning output?

Each result row in the CSV includes a reasoning column containing the model's per-code explanations in JSON format. These are intended to support human review: a researcher can inspect why the model assigned a given code and correct errors before using the codes in analysis.

Why does my emma / personal series score lower than norms-f?

See Known Limitations — Annotator biographical knowledge bias. The short answer: annotators who knew the dreamer personally applied family codes (husband, daughter, etc.) from the first dream, but those relationships are often never stated in the dream text. The classifier correctly applies the codebook rules to the text it sees, which produces disagreement with the human codes. Use non-family F1 as your primary metric for evaluating the classifier.

Can I contribute a new coding module?

Yes — contributions welcome. Each module is a self-contained Python script. Follow the structure of characters.py: codebook as a module-level string constant, few-shot examples as a list, call_claude() for LLM inference, evaluate() for F1 computation, and a main() with argparse flags matching the existing interface.
